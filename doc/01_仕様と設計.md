# Snowflake × Databricks 不動産価格予測基盤 仕様と設計

> 機能仕様 + アーキテクチャ設計。プロジェクト全体像を伝える土台。
> 要件レベルの変更時に更新する。矛盾時は [`02_移行ロードマップ.md`](./02_移行ロードマップ.md) を正とする。

## 共通前提

- **目的**: 不動産価格予測を題材に、アプリケーション由来データを `GCS -> Snowflake -> dbt -> Databricks -> Snowflake` で処理する、DWH・ガバナンス・ML パイプラインを一気通貫で検証する。
- **入力 / 出力**:
  - 入力 = アプリケーションまたはバッチが出力する不動産取引データ、マスタデータ、地域データ
  - 出力 = 学習用マート、スコアリング対象マート、予測結果マート、BI / API 向けセキュア参照面
- **担当範囲**:
  - GCS への raw データ配置
  - Snowflake への取り込み
  - dbt による DWH レイヤリング
  - Snowflake 上のガバナンス設計
  - Databricks による特徴量生成、学習、実験管理、バッチスコアリング
  - Snowflake への予測結果書き戻し
- **スコープ外**:
  - Deep Learning 中心構成
  - Vertex AI 中心構成
  - BigQuery 中心構成
  - リアルタイム推論
  - 過度な Web アプリ開発
- **ユースケース**:
  1. アプリケーションデータを GCS へ配置し、Snowflake へ取り込む
  2. dbt で raw / staging / intermediate / mart の責務分離を検証する
  3. Databricks で表形式 ML の学習と実験管理を行う
  4. 予測結果を Snowflake へ戻し、BI / API 向けに提供する
- **開発環境**: Python、Snowflake SQL、dbt Core、Databricks Notebook / Job 定義
- **本番環境**: 学習用・検証用のクラウドデータ基盤。常駐アプリではなくデータ基盤 / ML パイプラインを主対象とする
- **言語 / フレームワーク**:
  - Python
  - FastAPI 想定
  - dbt Core
  - scikit-learn
  - LightGBM
  - MLflow
- **設定管理**: 非機密は `env/config.yaml`、ローカル秘密情報は `env/secret.yaml`、共有・本番秘密情報は Doppler（`doppler.yaml`）
- **CI/CD**: 現時点では未整備。将来的に SQL / dbt / Python の lint と検証コマンドを追加する
デザインパターンはできるだけ、データブリック提案のものを採用する

## 1. アーキテクチャ

このプロジェクトでは、Snowflake を DWH / ガバナンス基盤、Databricks を ML 加工 / 実験基盤、dbt を Snowflake 内変換管理として置く。

```text
App / Batch / API
   ↓
GCS
   ↓
Snowflake External Stage
   ↓
Snowflake RAW
   ↓
dbt
  staging / intermediate / mart
   ↓
Snowflake Governed Mart
   ↓
Databricks
  feature engineering / training / MLflow / batch scoring
   ↓
Snowflake Prediction Mart / Score Mart
   ↓
BI / API / dashboard
```

### コンセプト

- **Snowflake を DWH とガバナンスの中心に置く**: 取り込み、マート、権限制御、機微情報制御を Snowflake 側で担う
- **Databricks を ML 専用処理に寄せる**: DWH の恒常的変換をすべて Databricks に寄せず、特徴量生成、実験、学習、スコアリングを主責務とする
- **dbt を DWH 内変換の正規ルートにする**: 再利用される業務変換、品質テスト、マート作成は dbt に集約する
- **Deep Learning より表形式 ML を優先する**: 不動産価格予測では説明性、再現性、実務導入容易性を優先し、scikit-learn / LightGBM を中心にする

### 1.1 データフロー

#### 1. アプリケーション -> GCS

アプリケーションまたはバッチ処理から、不動産取引データを GCS に出力する。

想定格納先:

```text
gcs://realestate-ml/raw/properties/
```

想定データ:

- 物件 ID
- 所在地
- 都道府県
- 市区町村
- 最寄駅
- 駅距離
- 面積
- 間取り
- 築年数
- 建物種別
- 取引時期
- 取引価格

GCS は Snowflake 取り込み前の raw data landing zone として扱う。

#### 2. GCS -> Snowflake RAW

Snowflake External Stage を使い、GCS 上のファイルを Snowflake へ取り込む。

```text
GCS
  ↓
Snowflake External Stage
  ↓
COPY INTO
  ↓
RAW Tables
```

RAW 層の責務:

- 元データの保全
- 再処理可能性の確保
- 取り込み失敗時の調査容易化
- staging 以降との責務分離

想定テーブル:

- `RAW.PROPERTY_TRANSACTIONS`
- `RAW.PROPERTY_MASTER`
- `RAW.AREA_MASTER`
- `RAW.STATION_MASTER`

#### 3. Snowflake RAW -> dbt staging

dbt を使い、RAW から staging モデルを作成する。

staging 層の責務:

- カラム名の標準化
- 型変換
- NULL 処理
- 単位変換
- 不正値除去
- 日付・年月の正規化

例:

```text
RAW.PROPERTY_TRANSACTIONS
  ↓ dbt
STG.STG_PROPERTY_TRANSACTIONS
```

#### 4. dbt staging -> intermediate -> mart

intermediate 層では、ML に必要な業務特徴量の前処理を行う。

```text
staging
  ↓
intermediate
  ↓
mart
```

想定 intermediate:

- `INT.PROPERTY_FEATURE_BASE`
- `INT.AREA_PRICE_AGGREGATES`
- `INT.STATION_DISTANCE_FEATURES`
- `INT.TIME_FEATURES`

想定 mart:

- `MART.REALESTATE_TRAINING_DATA`
- `MART.REALESTATE_SCORING_TARGETS`

`MART.REALESTATE_TRAINING_DATA` は Databricks が読み込む学習用データセットとする。

#### 5. Snowflake mart -> Databricks -> Prediction mart

Databricks は Snowflake Connector を使い、Snowflake の学習用 mart を読み込む。

```text
Snowflake MART.REALESTATE_TRAINING_DATA
  ↓
Databricks
  ↓
Feature Engineering
  ↓
MLflow
  ↓
Model Training
  ↓
Batch Scoring
  ↓
Snowflake MART.REALESTATE_PRICE_PREDICTIONS
```

## 2. 機能仕様

### 2.1 データ取り込み機能

- アプリケーションまたはバッチから生成したデータを GCS に保存する
- Snowflake External Stage + `COPY INTO` で raw テーブルへ取り込む
- CSV / JSON / Parquet を想定するが、初期主対象は CSV / Parquet とする
- 取り込み後も raw データを再処理可能な形で保全する

### 2.2 DWH 変換機能

dbt の責務は Snowflake 内で再利用される業務変換とマート作成である。

dbt で扱うもの:

- `raw -> staging`
- `staging -> intermediate`
- `intermediate -> mart`
- データ品質テスト
- `not null / unique / accepted values`
- mart 作成
- ドキュメント生成

Databricks で扱うもの:

- 学習用特徴量生成
- train / valid split
- scikit-learn / LightGBM 学習
- MLflow 実験管理
- バッチスコアリング
- Snowflake への予測結果書き戻し

### 2.3 ガバナンス機能

Snowflake では DWH、マート、予測結果に対してガバナンス制御を適用する。

#### ロール設計

想定ロール:

| ロール | 用途 |
|---|---|
| `SYSADMIN` | オブジェクト管理 |
| `DATA_ENGINEER_ROLE` | raw / staging / mart 作成 |
| `ANALYST_ROLE` | mart 参照 |
| `ML_ENGINEER_ROLE` | Databricks 連携用 |
| `BI_ROLE` | BI 向け secure view 参照 |
| `GOVERNANCE_ROLE` | masking / row access policy 管理 |

#### Masking Policy

対象例:

- 住所詳細
- 緯度経度
- 物件所有者情報
- 取引相手情報
- 詳細所在地

制御イメージ:

- 一般ユーザー: 詳細住所はマスク
- `ML_ENGINEER_ROLE`: city / area レベルは参照可能、exact address は原則参照不可
- `DATA_ENGINEER_ROLE`: 検証用途で限定参照

#### Row Access Policy

地域・部門・用途に応じた行レベル制御を想定する。

例:

- 北海道担当: `prefecture = '北海道'`
- 関東担当: `prefecture IN ('東京都', '神奈川県', '千葉県', '埼玉県')`
- `ML_ENGINEER_ROLE`: 全地域参照可能、ただし機微カラムはマスキングで制御

#### Secure View

BI や業務利用向けには、直接 mart を見せず Secure View を提供する。

想定:

- `SECURE_VIEW.REALESTATE_PRICE_DASHBOARD_VIEW`
- `SECURE_VIEW.REALESTATE_PREDICTION_SCORE_VIEW`

目的:

- 不要カラムの隠蔽
- マスキング適用済みデータ提供
- BI 利用者向けの安定 IF
- mart 構造変更の影響吸収

### 2.4 ML 機能

タスクは不動産取引価格の回帰予測とする。

#### target

```text
target = transaction_price
```

#### 想定特徴量

| 特徴量 | 内容 |
|---|---|
| `area_sqm` | 面積 |
| `building_age` | 築年数 |
| `distance_to_station_min` | 駅徒歩分 |
| `prefecture` | 都道府県 |
| `city` | 市区町村 |
| `building_type` | 建物種別 |
| `layout` | 間取り |
| `transaction_year` | 取引年 |
| `transaction_quarter` | 取引四半期 |
| `avg_area_price` | 地域平均価格 |
| `price_per_sqm_area_avg` | 地域別平米単価平均 |

#### モデル

Baseline:

- `LinearRegression`
- `RandomForestRegressor`

Main:

- `LightGBM Regressor`

使用ライブラリ:

- scikit-learn
- lightgbm
- pandas
- numpy
- mlflow

Deep Learning は使わない。

理由:

- 表形式データでは LightGBM が強いケースが多い
- 説明しやすい
- 実務導入しやすい
- 学習コストが低い
- MLOps 検証の主眼がモデル複雑性ではない

#### 評価指標

| 指標 | 用途 |
|---|---|
| `MAE` | 平均的な価格誤差 |
| `RMSE` | 大きな外れ値への感度 |
| `MAPE` | 相対誤差 |
| `R2` | 説明力の参考値 |

主評価は `MAE / RMSE` とする。

#### 予測結果テーブル

Databricks で作成した予測結果は Snowflake へ戻す。

想定:

`MART.REALESTATE_PRICE_PREDICTIONS`

カラム例:

| カラム | 内容 |
|---|---|
| `property_id` | 物件 ID |
| `predicted_price` | 予測価格 |
| `actual_price` | 実価格 |
| `prediction_error` | 予測誤差 |
| `model_name` | モデル名 |
| `model_version` | モデルバージョン |
| `scored_at` | スコアリング日時 |
| `feature_snapshot_date` | 特徴量スナップショット日 |

## 3. 設計上の決定事項

### 3.1 採用したアプローチ

- **Snowflake を DWH / ガバナンス基盤に置く** — データ取り込み、マート、RBAC、Masking Policy、Row Access Policy、Secure View を一元管理しやすいため
- **dbt を Snowflake 内変換の正規ルートにする** — 再利用される業務変換と品質テストを SQL ベースで管理しやすいため
- **Databricks を ML 専用処理へ寄せる** — DWH 変換と ML 変換の責務分離がしやすく、MLflow で実験管理しやすいため
- **表形式 ML を中心にする** — 実務説明性、再現性、導入容易性を優先するため
- **予測結果を Snowflake へ戻す** — BI / API / ダッシュボードから利用しやすい提供形に戻すため

### 3.2 採用しなかったアプローチ

- **Deep Learning 主体** — 今回の主題がモデル複雑性ではなく、データ基盤と ML パイプラインの一気通貫検証であるため
- **Vertex AI 中心構成** — GCP 専用色が強くなり、Snowflake / Databricks 連携の主題が薄くなるため
- **BigQuery 中心構成** — 今回は Snowflake を DWH とガバナンス中心に置くため
- **リアルタイム推論** — 初期優先度はバッチスコアリングと DWH 戻しであるため
- **過度な Web アプリ開発** — 主眼は UI ではなく、データパイプラインと ML 基盤設計であるため

## 4. 非機能要件

- **性能 / スケール**: 初期対象は学習・検証用途。不動産サンプルデータから始めるが、将来的に raw -> mart -> scoring の責務分離が壊れないことを重視する
- **セキュリティ / 認証**: Snowflake RBAC、Masking Policy、Row Access Policy、Secure View を前提にし、機微カラムの露出を抑える
- **可用性 / 監視**: 常駐アプリよりバッチ基盤を主対象とするため、再実行性と調査容易性を優先する
- **再現性**: raw データ保全、dbt モデル管理、MLflow 実験管理により、学習・変換・スコアリングの再現経路を残す
- **保守性**: Snowflake / dbt / Databricks の責務分離を守り、どこで変換するかを曖昧にしない
- **説明可能性**: Deep Learning ではなく、LightGBM を中心とした表形式 ML により、予測ロジックの実務説明性を確保する
- **拡張性**: BI / API 向けの Secure View や prediction mart を通して、後続の利用面追加に備える
