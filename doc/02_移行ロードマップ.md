# 移行ロードマップ

> 本書は [`01_仕様と設計.md`](./01_仕様と設計.md) を実行順へ落とした作業計画書である。`01` が「何を作るか」の正本、`02` が「どういう順序で作るか」の正本とする。参考プロジェクトは `/home/ubuntu/repos/study-databricks-gcp-pipeline` とし、そこにある「end-to-end が通る最短導線」「成果物の責務分離」「検証済み導線を文書に固定する」設計姿勢を取り込む。

## 0. 前提

### 0.1 成果物

本リポジトリの成果物は、住宅価格予測を題材にした以下の検証系である。

```text
アプリ / バッチ / CSV
  -> GCS
  -> Snowflake RAW
  -> dbt staging / intermediate / mart
  -> Databricks feature engineering / training / batch scoring
  -> Snowflake prediction mart / secure view
```

単なる学習メモではなく、Snowflake と Databricks の責務分離を理解しながら、表形式 ML を含むデータ基盤の通し構成を再現できる状態を目標にする。

### 0.2 設計の正本

- 仕様、責務分離、非機能要件、スコープ境界は [`01_仕様と設計.md`](./01_仕様と設計.md) を正とする。
- 本書は `01` の内容を変更しない。変更が必要な場合は先に `01` を更新し、その後 `02` を同期する。

### 0.3 初期スコープ

初期スコープは以下に固定する。

- データ着地先は Snowflake
- 変換の主役は dbt
- ML 実装の主役は Databricks
- 推論結果の返却先は Snowflake
- 方式はバッチ前提
- 対象 ML は表形式回帰
- 主力モデルは LightGBM

### 0.4 初期スコープ外

以下は初期 Phase では扱わない。

- Deep Learning を前提にした構成
- Vertex AI 中心の MLOps
- BigQuery 中心の DWH 構成
- リアルタイム推論 API
- Stream 処理の常時運用
- 重い Web アプリ
- 本番監視、当番、通知運用の完成

## 2. 段階構築計画

参考プロジェクトにならい、最初から全機能を同時に作らず、責務ごとに検証可能な Phase へ分解する。

### Phase 0. 骨格定義

#### 目的

実装前に、何をどこへ置くかを固定し、後続フェーズの迷いをなくす。

#### 作るもの

- 参考プロジェクトからの初期コピー
  - `src/reference/...`
  - `src/data/reference/...`
- `src/sql/`
  - Snowflake DDL / DML / governance SQL
- `src/dbt/`
  - dbt project 本体
- `src/databricks/`
  - notebook, job, feature, training, scoring 用資産
- `src/data/`
  - 学習用のサンプル CSV または fixture
- `src/docs/` または同等の補助メモ
  - 実行例、補足メモ、画面キャプチャ保管先
- `env/`
  - 接続設定テンプレート、環境変数一覧

#### この段階で決めること

- ディレクトリ命名
- Snowflake 側の database / schema 分割方針
- dbt の layer 命名
- Databricks 側の notebook / workflow / experiment の責務
- サンプルデータの持ち方
- ローカル実行とクラウド実行の切り分け

#### 完了条件

- `src/` 配下の責務分離が文章だけでなく構成として定義されている
- `01` にある想定ディレクトリ構成と矛盾しない
- 各層の成果物が `03_実装カタログ.md` に将来転記できる粒度になっている

### Phase 1. Snowflake RAW 着地

#### 目的

入力データを Snowflake に安全に着地させ、後続の dbt が読める RAW 基盤を作る。

#### 作るもの

- Snowflake database / schema 作成 SQL
- RAW テーブル作成 SQL
- stage / file format / COPY INTO または同等の ingest 手順
- サンプル入力データ
- 接続確認手順

#### 実装観点

- GCS からの着地経路を先に固める
- 1 回目は手動実行でもよい
- まずは 1 データセットで良いので、RAW に確実に入ることを優先する
- スキーマドリフト吸収や自動化は後段に回す

#### 完了条件

- サンプルデータが Snowflake RAW に入る
- 行数確認 SQL がある
- 失敗時にどこで止まったか分かる

### Phase 2. dbt 変換レイヤ

#### 目的

RAW から staging / intermediate / mart を作り、分析・学習に耐える整形済みテーブルを用意する。

#### 作るもの

- dbt project 初期化
- source 定義
- staging model
- intermediate model
- mart model
- schema test
- `dbt run` / `dbt test` の実行手順

#### 実装観点

- 参考プロジェクトの「SQL を責務ごとに固定する」考え方を踏襲し、dbt 側も layer ごとの責務を明確にする
- RAW ではビジネスルールを持ち込まない
- staging では型、命名、欠損整理
- intermediate では join、派生特徴量の材料作成
- mart では分析・学習入力に近い形まで整理

#### 完了条件

- `dbt run` が最後まで通る
- 主要 model に schema test が付く
- 学習に使う入力テーブルが 1 本に定まる

### Phase 3. Snowflake ガバナンス

#### 目的

学習・分析用途でも、列制御と行制御を含む統制を組み込む。

#### 作るもの

- role / grant SQL
- masking policy
- row access policy
- secure view
- 利用者別の参照例

#### 実装観点

- `01` で定義した RBAC, masking, row access, secure view を最小構成で実装する
- 個人情報や機微列をどこで制御するかを固定する
- mart 本体と公開 view を分ける

#### 完了条件

- 役割別に見える列、見えない列が再現できる
- secure view 経由の公開導線がある
- ガバナンスが SQL で再現可能になっている

### Phase 4. Databricks 学習基盤

#### 目的

Snowflake mart を読み、Databricks 上で特徴量加工、学習、評価、推論まで通す。

#### 作るもの

- Snowflake から読み込む notebook または script
- feature engineering notebook
- baseline model notebook
- LightGBM 学習 notebook
- 評価指標出力
- batch scoring notebook

#### 実装観点

- 先に baseline を作り、その後 LightGBM へ進む
- notebook を無秩序に増やさず、`ingest`, `feature`, `train`, `score` 程度に責務を分ける
- MLflow を使う場合はこの Phase で最小導入する
- まずは単一ターゲット、単一目的変数に絞る

#### 完了条件

- Snowflake mart を Databricks から読める
- baseline と LightGBM の両方で評価指標が出る
- 予測結果を DataFrame として生成できる

### Phase 5. Snowflake への書き戻し

#### 目的

予測結果を Snowflake に戻し、BI や分析で再利用できる形にする。

#### 作るもの

- prediction table または prediction mart
- 書き戻し notebook / script
- 予測値、スコア日時、モデル識別子を持つスキーマ
- 公開用 secure view

#### 実装観点

- 書き戻し先は学習入力 mart と分離する
- overwrite / append の方針を決める
- モデル評価と予測結果を混ぜない

#### 完了条件

- 予測結果が Snowflake に入る
- 下流が参照する公開 view が定まる
- 再実行時の更新方針が文章化されている

### Phase 6. E2E 固定化

#### 目的

通った実行手順をドキュメントへ固定し、再現可能な教材にする。

#### 作るもの

- `README.md` のクイックスタート更新
- `03_実装カタログ.md` の成果物逆引き
- `04_運用.md` の日次・反復運用
- 必要なら画面キャプチャや実行ログ要約

#### 実装観点

- 参考プロジェクトのように「検証済み導線」を残す
- どの順序で叩けば最短で動くかを明示する
- 失敗しやすいポイントを運用ドキュメントへ寄せる

#### 完了条件

- 初学者が上から読んで実行順を追える
- `01`, `02`, `03`, `04`, `README` の間で矛盾がない
- end-to-end の成功条件が文章で再現できる

## 4. End-to-end 検証

本リポジトリの受け入れ確認は、以下が上から順に通ることをもって成立とする。

### 4.1 正常系

1. サンプルデータが GCS に配置される
2. Snowflake RAW に ingest できる
3. dbt staging / intermediate / mart が通る
4. Databricks で学習入力を読める
5. baseline model の指標が出る
6. LightGBM の指標が出る
7. batch scoring 結果が生成される
8. 予測結果が Snowflake prediction mart に戻る
9. secure view 経由で下流参照できる

### 4.2 異常系

- GCS 入力が存在しない
- Snowflake 接続情報が不足している
- RAW テーブル定義と入力列が一致しない
- dbt test が失敗する
- Databricks 側で特徴量列が欠落する
- 書き戻し先テーブルの権限が不足する

### 4.3 品質系

- staging で型崩れが放置されていない
- mart の粒度が学習用途に合っている
- ガバナンス付き view で制御が効いている
- baseline と LightGBM の比較結果が残る
- 予測結果に生成日時または run 識別子がある

### 4.4 文書整合

- `01` のアーキテクチャ図と `02` の Phase が対応している
- `03_実装カタログ.md` で各成果物を逆引きできる
- `04_運用.md` の日次手順が `02` の完了後にそのまま使える

## 7. 現時点の実行順

迷ったら以下の順で進める。

1. `src/` 骨格を切る
2. Snowflake RAW ingest を通す
3. dbt で学習入力 mart を作る
4. Snowflake ガバナンスを最小導入する
5. Databricks で baseline -> LightGBM の順に通す
6. 予測結果を Snowflake へ戻す
7. `README`, `03`, `04` を同期して E2E を固定する

この順序は、参考プロジェクトの「最小導線を先に通し、あとから全体を太くする」進め方を、本リポジトリの Snowflake × dbt × Databricks 構成へ読み替えたものである。
